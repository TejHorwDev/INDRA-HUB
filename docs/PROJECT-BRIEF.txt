HOW TO USE THIS DOCUMENT
------------------------
This is a complete, self-contained description of the INDRA HUB project: what it
is, every feature that exists, how it is built, how it ships, what is proven,
and what is still missing. Read it as the full context for the codebase. It is
written so that nothing else is needed to start working on the project.

If you are an AI assistant receiving this: treat the "RULES THAT MUST NOT BE
BROKEN" section as hard constraints, and treat the "KNOWN LIMITATIONS" section as
the honest list of what is unfinished. Do not describe features that are not in
this document — they do not exist.


1. WHAT IT IS
-------------
INDRA HUB is a local-first desktop workspace for writing documents and turning
them into presentations. It runs entirely on the user's machine: accounts,
projects, documents, decks and settings all live in a single SQLite file. It
works with no network connection and needs no server.

Around that core sit three things:
  - teams: projects with an owner and members, with per-project access checks
  - an administration panel: a separate identity with its own session, able to
    manage accounts, projects, content, activation keys, app-wide switches and
    an audit log
  - a self-updater: the installed app updates itself from GitHub Releases by
    replacing a small code payload, without ever downloading or running an
    installer

The product constraint that shaped everything: the user installs a Windows
installer ONCE. Every later update must arrive inside the running app. The user
explicitly rejected "downloads the new installer and runs it".

component library, no HTTP client beyond Electron's net/fetch.


4. ARCHITECTURE
---------------
Three processes, one rule: the renderer never touches the filesystem or the
database directly.

  src/main/index.ts        main process: window, menu, IPC registration, CSP,
                           single-instance lock, --reset-admin handling
  src/main/bootstrap.ts    the entry point of the packaged app (see section 8):
                           decides whether to run the installed code or a
                           downloaded payload
  src/main/ipc/index.ts    every IPC handler; each one validates its input and
                           resolves the caller itself (never trusts the renderer)
  src/main/services/*      business logic, one module per area:
                           auth, projects, users, documents, presentations,
                           graph, admin, activation, backend, settings, updates
  src/main/lib/*           payload (update storage + bootstrap), convert
                           (document → deck), sanitize, password, validation,
                           errors
  src/main/db/*            schema.ts (tables + migrations), database.ts
                           (connection, pre-migration backups)
  src/preload/index.ts     the typed bridge; the only surface the UI can call
  src/renderer/src/...     React UI
  src/shared/types.ts      the single source of truth for every shape crossing
                           IPC, and for constants like theme lists

Renderer isolation: sandbox on, contextIsolation on, nodeIntegration off, and a
Content Security Policy in the packaged app. The renderer talks to the main
process only through `window.indra`, defined in the preload; every call returns
`{ ok: true, data }` or `{ ok: false, error }` and the UI unwraps it in
`src/renderer/src/lib/api.ts`.

59 IPC channels exist, all namespaced: app:*, auth:*, projects:*, documents:*,
presentations:*, graph:*, updates:*, backend:*, admin:*.


5. FEATURE INVENTORY
--------------------

5.1 Accounts and sessions
  - Signed-out shell (1.6.3): the form sits in one centred column on an
    edgeless veil. No card, no border, no wordmark and no foot line — the only
    things on the screen are the heading, the fields, one button and one link.
    With the administrator's background video installed the film plays behind
    that column under a darkening and a blur, both faded out radially so the
    edges fall back to the desktop instead of framing a box. The column centres
    with margin-block so it still scrolls on a short window rather than being
    clipped.
  - Local registration with username, display name, email, password
  - Sign in with username OR email
  - scrypt hashing with per-record salt; constant-time verification
  - Sessions remembered for 30 days in the local database
  - Login throttling: 5 failed attempts locks sign-in for 15 minutes
  - Self-service: change display name / email, change password, delete account
    (password-confirmed)
  - Registration can be closed by the administrator
  - Registration can require an activation key
  - Maintenance mode: closes the WORKSPACE, never the front door. Signing in and
    registering always work; a signed-in account lands on the administrator's
    maintenance message, and every data call is refused in the main process
    while it is on. The administration panel stays reachable so it can be lifted
    from inside. Nothing on the maintenance screen points at administration.
  - The maintenance screen is a composed card, not a text column: status
    eyebrow with a live pulse, an automatic-checking pill, the administrator's
    message as a quoted panel, a three-part fact strip (account, workspace,
    last check), a quiet note, "Check now" / "Sign out", and an indeterminate
    activity line along the bottom edge. Same hairline grid as the sign-in
    canvas, light and dark, and it collapses to one column at narrow widths.

5.1b Offline (1.7.0, completed in 1.9.0)
  - The main process answers `net.isOnline()` every four seconds, re-reads it
    when the window is focused, and tells every window when it changes. No
    ping, no DNS lookup, no traffic: the operating system's own view.
  - **No credential is accepted with no route out (1.9.0).** Signing in and
    registering are refused below the UI: offline they could only compare a
    password against a hash in the same file, which proves nothing about who
    the person is. The refusal is a typed error with a sentence, not a dead
    button, and it leaves no session behind.
  - **Signed out and offline, the sign-in form is not shown at all.** The app
    opens on the offline screen: what is offline, why signing in needs a
    connection, and one action — `Go offline`.
  - `Go offline` opens the **offline workspace**: a local profile named
    `offline` (shown as "This PC") that owns the work written there. Its
    password is 32 random bytes, hashed and discarded in the same statement,
    so nobody can sign in as it; sign-in by that name is refused explicitly as
    well as practically. The session is marked `mode: 'offline'`, and every
    screen that needs an account refuses while it is open — the cloud copy on a
    project page reads "Needs an account", and the cloud IPC calls answer
    AUTH_REQUIRED.
  - **Offline work is adoptable.** Projects written in the offline workspace
    are listed on the Projects screen under "N projects written offline", with
    one action: `Move into my account`. Ownership moves — nothing is copied or
    deleted, ids, versions and history survive — and the offline workspace is
    left empty for next time.
  - An offline session lasts one day and does not survive a restart into a
    connection: starting up online returns to the account screen rather than
    silently running yesterday's mode.
  - Signed in and the connection drops: the session (remembered 30 days) still
    works and the workspace narrows, which is the point of local-first. What
    1.9.0 forbids is proving a *new* identity offline.
  - Working offline is also a choice: the sign-in screen offers `work offline`
    on a connected PC. The same workspace opens, and `Sign in instead` in
    Settings returns to the account screen.
  - The renderer mirrors it through ConnectivityProvider, with the browser's
    online/offline events as a second pair of eyes.
  - Offline, the app is the writing tool: the rail keeps Documents,
    Presentations, Projects and Settings; everything else redirects to
    Documents instead of rendering half-alive. The caption carries a quiet
    OFFLINE pill and the rail's only heading is OFFLINE.
  - Documents and Presentations are cross-project libraries (every document
    and deck the account can reach, most recent first, project named on each
    row). They are the offline workspace and nothing else: online, a project is
    the container, so the rail does not list them, the palette does not offer
    them, and /documents redirects to the project list. (1.8.1 — 1.8.0 briefly
    had them in both places, which was one way to find work too many.)
  - The rule lives in lib/nav.ts as plain data, so `npm run sim:offline`
    asserts it rather than a screenshot: online the rail has no Documents or
    Presentations entry; offline it has both, in one group.
  - Nothing in the offline path touches the network: sign-in, registration,
    projects, documents, presentations, settings and the maintenance screen
    are all SQLite reads and writes.

5.1c Where work is kept (1.7.0)
  - The working copy is SQLite on the machine. It has never needed a
    connection and it is what every screen reads.
  - "Save a copy" on a project writes one .indrahub file through the system
    save dialog: project name and description, every document's blocks, every
    presentation's slides and its theme. Self-contained — no ids to resolve.
  - "Open a saved project" on the Projects screen reads one back as a NEW
    project owned by whoever opened it, so the same file can be opened twice,
    or on another machine, without touching the original.
  - Imported files are parsed, shape-checked, and pushed through the same
    block sanitiser as a typed document; a file that breaks halfway leaves no
    half-made project behind.
  - The other destination is the cloud, and it arrived in 1.8.0 (5.1d). A
    project page offers both: "Save to PC" writes the file above, "Save to
    cloud" writes the copy in section 10. Either, or both, or neither.

5.1d The cloud copy (1.8.0)
  - Each installation is its own account in Supabase. On the first cloud save
    the main process registers an auto-confirmed identity with a generated
    address and a 32-byte password, and keeps it sealed by the OS keystore.
    The password is kept, not just the refresh token: a copy this PC can no
    longer authenticate to is not a backup.
  - Why an identity at all: the cloud tables are governed by `auth.uid()`. A
    publishable key alone can read and write nothing — which is the point of
    the RLS layer — so the choice was to weaken the policies or give each
    installation a real user. The second is the only one that keeps two
    customers' work apart. There is no service key in the app, ever.
  - Push is a mirror, not a merge: the cloud project's documents and decks are
    replaced with this project's. Merging two divergent document trees without
    asking is how people lose work. Rows are namespaced
    (`<project>:d:<document>`, `<project>:p:<presentation>`, `<deck>:s:<slide>`)
    so a push is idempotent and two projects can never collide on a primary key.
  - The project page reads its cloud state from disk, so it can say "Saved 4
    minutes ago · newer work here" with no connection. The button itself is
    inert offline, and the main process refuses all five cloud calls with the
    machine has no route out — the renderer is not the thing deciding that.
  - The Projects screen lists cloud copies in a second shelf below your own
    projects (1.8.1 moved it out of the library, which became offline-only).
    That shelf is not fetched and not drawn offline. Offline is this PC only,
    always.
  - Pulling a cloud project lands as a NEW local project through the same
    restore path an imported file uses, so it is sanitised by the same code.
    It remembers which cloud copy it came from, so saving it again updates that
    copy rather than making a second one.
  - Moving the copy to a second PC: Settings → Cloud → "Move to another PC"
    produces a transfer code (this PC's cloud identity, encoded), and the other
    machine adopts it under "Use a code from another PC". The panel says what
    it is — a credential. Adopting replaces that PC's identity and clears its
    local cloud badges, and nothing on either disk is deleted.
  - Proven by `npm run sim:cloud` against a stand-in PostgREST/GoTrue that
    enforces the same policies (27 checks: offline sends nothing, per-install
    isolation, replace-not-merge, transfer, adoption, sealed identity), plus
    rolled-back probes against the real database: an owner insert with
    `owner_id = indra_uid()` accepted, its documents/decks/slides accepted,
    its delete-and-rewrite accepted, and a second identity reading 0 rows and
    changing nothing.

5.1f Finish, motion and type (1.9.1)
  - The signed-out panel's offline route is a real button on a hairline divider,
    not a link inside a sentence: icon, label, one line of explanatory text
    under it. Same action, legible as an action.
  - Page headers share one frame (`page-head` / `page-description` /
    `page-actions`) across every screen, so the title, its description and the
    actions on the right line up identically on Projects, Documents, Settings
    and a project's own page; on a narrow window the actions take their own
    line instead of squeezing the title.
  - Type: headings break by sentence (`text-wrap: balance`), paragraphs avoid
    orphans (`pretty`), and every number that gets scanned — counts, dates,
    versions, stats — is tabular.
  - Controls: one focus ring (a 2px canvas gap and an accent halo) for buttons,
    rail items, rows, links and window controls; a press is half a pixel and a
    hair of scale; rows answer the pointer by a pixel and a border.
  - Motion: route arrival, staggered rows, the active project tab wiping in
    from the left, the rail's accent on the current section, and a fade on a
    theme change. All transform/opacity/colour, and `prefers-reduced-motion`
    zeroes the lot.

5.2 Home, teams and projects
  - Home is the first screen after signing in and the first item in the
    sidebar. Two panels and no more: the account (monogram, name, handle,
    email, member since, a link to settings) and the team.
  - One team per owner, created in place, renamed in place, deleted behind a
    confirmation. The roster lists the owner first, then members; a member is
    removed from the row itself.
  - **Joining is consensual (1.9.3).** Choosing a person sends them an
    invitation; it does not enlist them. Nothing of the team — or of a project —
    is reachable until they accept, because access is derived from the
    membership tables and acceptance is the only thing that writes one. This
    was a correction, not a refinement: adding somebody used to put them on a
    roster, and in a project, with no way to notice or refuse.
  - An invitation is a row in this installation's database: one account invited
    for one team or one project, with a status (`pending`, `accepted`,
    `declined`, `revoked`, `cancelled`) and the time it was answered. A
    partial unique index allows one pending question per person and target, so
    double-clicking a button cannot send two.
  - The invitee answers on Home: a section above the panels names what it is for,
    who asked, and offers Accept and Decline. The rail carries a count on Home
    while one is waiting, and an invitation that arrives while the app is open
    is announced once in a toast. A poll on focus and every 30 seconds is how it
    is noticed — there is no server pushing, because there is no server.
  - Declining is an answer, not a deletion: the owner is not left waiting, the
    row stays as a record, and re-inviting the person later is a deliberate act
    rather than an automatic one. The invited person cannot withdraw a question
    themselves; only the owner of the team or project can revoke one, and even
    then it is recorded as revoked rather than erased.
  - Until it is answered, the person appears on the owner's roster marked
    "invited", with their address and a Cancel action, and is filtered out of
    the search so the same question cannot be sent twice. Their `memberCount`
    does not change — the count is people with access, not people asked.
  - Deleting a team, or a project, cancels the questions it left open; an
    invitation whose target no longer exists cannot be accepted.
  - Invitations are local to an installation, like accounts. They are not a
    cloud object and do not travel to another PC by themselves.
  - **People are found by email, not by name (1.9.2).** Names repeat, and an
    initials avatar makes two people with the same name look like one person,
    so the search field asks for the address the account was registered with.
    The match is EXACT and case-insensitive — no prefix, no wildcards — which
    is both what makes it unambiguous and what keeps it from being used to walk
    the account table one letter at a time. What comes back shows the person's
    name and their address, because the name is what the decision is made on.
  - The same rule applies to a project's members, and both filter in SQL: never
    the owner, never somebody already on the roster or the project, never a
    suspended account. A half-typed name is refused before it reaches the
    table.
  - Being a member of somebody else's team is read-only and shows under
    "Member of"; ownership is checked in the service on every write, not in
    the renderer.
  - **A team is a standing yes for the projects its owner starts (1.9.4).**
    This corrects 1.9.3, which made joining consensual but stopped one step
    short: a colleague could accept the team invitation and still open nothing,
    because membership and project access were two unrelated questions. The
    team is the group of people you work with, so it now means what it says —
    everyone on it can open every project its owner owns, read and write the
    documents, convert them into decks and save the decks.
  - The rule is derived, not stored: access is owner, OR an accepted project
    invitation, OR a team membership of the project's owner. Nothing is copied
    into a table, so removing somebody from the team closes their projects the
    same moment, and a project created after they joined opens to them without
    a second invitation.
  - The screens say which way in a person used. The project's team card labels
    a row "Team" or "Member", the overview says "through The studio" or
    "invited", and the card in the Projects list carries the same badge. The
    new-project dialog states who will be able to open it before it exists.
  - Team access is taken away through the team, not through a project row:
    removing a team member's individual project row is refused with that
    sentence rather than silently doing nothing. Invited outsiders — people not
    on the team — are still removed row by row.
  - Accepting a project invitation opens the project; accepting a team
    invitation says that the owner's projects are now on their Projects page.
  - What a team does **not** grant: the head developer's account, their other
    accounts' projects, or any admin reach. A member still cannot invite,
    remove, rename or delete; the shape of the project stays the owner's.
  - Teams and projects are still separate objects: deleting a team leaves every
    project, document and account where it was — it only closes the door that
    membership had opened.
  - **A project can span two PCs (1.9.5).** The head developer invites an
    address through the cloud (`supabase/sharing.sql`), the person on the other
    machine accepts on Home, and the project is brought down as a real local
    project: its documents, decks, slides and people, with this PC's own ids and
    a row per item recording which cloud item it came from. Their copy names the
    head developer in the roster and is marked as shared; local member actions
    stay refused, because the shape of a project is still the owner's.
  - The two copies are kept in step by an explicit **Sync** on the project page,
    never silently. Each item remembers a SHA-256 of the version both sides last
    agreed on, so "changed since" is answered by content rather than by
    comparing two machines' clocks. Pull runs before push: a change made
    elsewhere lands first, then this PC's changes go out, guarded by the version
    they replaced.
  - An item changed on both PCs is a **conflict**, not a merge: nothing is
    written, both copies are left exactly as they are, and the project says how
    many there are and offers "Keep mine" or "Take theirs". Answering writes the
    choice and the next sync settles it. Silently merging two edits of one
    document is how a person loses a paragraph they wrote.
  - "Save to cloud" is the first save and only that; once a copy exists the
    button is **Sync**, and the replace-everything push is refused on a project
    that has somebody else's work in it — it would delete the rows that work is
    in.
  - Cloud identity is now **per account**, not per installation: two people
    signing in on one PC are two different people in the cloud, and an
    invitation addressed to one of them cannot be answered by the other. An
    installation's pre-1.9.5 identity is adopted by the first account that
    reaches the cloud, so existing copies keep working.
  - What this does not do yet: deleting a shared document deletes it on this PC
    only (propagating a delete is a product decision, not an oversight), there
    is no live co-editing or presence, and two people editing the same document
    at the same instant still meet a conflict rather than a merge.
  - **The surface was rebuilt as a system, not repainted (1.9.6).** The dark
    canvas moves from near-black to the matte charcoal a native Windows app
    sits on (#101113), panels step up through #16181B and #1B1D21, and the
    separation between them is one hairline (#26282D) rather than a glow. Light
    mode keeps its paper canvas. The accent deepens to #B94250 so a filled
    button reads as wine rather than pink.
  - One control height (32px), one radius (6px), one weight (550); headings lose
    a step (page title 24 → 20px, panel labels 10px with 0.1em tracking), and the
    window gets a 44px caption bar, thin neutral scrollbars, and a flat canvas
    with no gradient wash.
  - The rail is a list of places: 32px rows, muted glyphs, a hairline indicator
    on the selected row. Every existing destination is unchanged.
  - Projects are a two-column shelf of cards with a glyph, a name, two lines of
    description and the same two facts as before (people, last change). The
    cloud shelf uses the same card, because it is the same kind of thing.
  - Page frames widen to 1180px, padding tightens to 28/24, and the rule under
    a header is gone where no tabs need it. Header actions are outlined
    secondaries with one primary; inside a toolbar a ghost button is a label
    until hovered, so dense editors do not become a wall of boxes.
  - Nothing was removed, re-routed, renamed or re-wired: 1.9.6 changes tokens,
    spacing, typography and the project card's markup only. All ten
    simulations and the typecheck/build pass unchanged. 2.0.0 adds the research
    panel and the credit screens in the same monochrome language: hairlines,
    tabular figures, one filled control.
  - **The interface is monochrome (1.9.7).** Black, greys and white; no hue
    anywhere. Emphasis is contrast, weight and space: the primary action is a
    white pane on charcoal (black on paper in light mode), selection is a 2px
    white mark on the active row, chips are outlines rather than fills, and
    avatars are neutral greys instead of tinted circles. Destructive actions are
    marked by weight and an underline; the confirmation dialog carries the
    warning. Errors keep their icon and copy rather than a colour.
  - Canvas \`#08090a\`, panels \`#0f1012\`, raised \`#1b1c20\`, one hairline at
    \`#202126\`. The window's own background matches the canvas, so resizing
    never flashes a different black.
  - **Home is a dashboard, not a sign-in card.** The identity block and the team
    are one band of equal height across the page, and a "Recent projects" strip
    below carries the three most recently touched projects — the same rows the
    Projects page shows, in the order it already receives them, with no invented
    statistics. Choosing one opens it.
  - Create, rename, delete projects; each has a description
  - Owner/member model stored in project_members, plus team access derived at
    read time
  - Invite members by exact email address; the matched account's name and
    address are shown so the choice is made by name, and the invitation is

5.11 AI research and credits (2.0.0)
  - **Where the model lives.** Not in the app. `supabase/functions/ai` (the
    Edge Function `indra-ai`) holds the provider key in the project's
    environment and is the only thing that calls a model. The desktop app sends
    its own cloud token, the open document as plain text, the current selection,
    the question and the last few turns; nothing else. No key exists in the
    build, in settings, or in a log — `sim:ai` checks that no provider
    credential is ever placed in a request the app makes.
  - **Write.** One turn, inside the document editor: ask for a paragraph, a
    rewrite or a sharper argument. The model receives the document and writes
    in its voice. A selection is sent as the passage to work on.
  - **Research.** Plan → search → read → synthesise. The model first returns
    3 (standard) or 6 (deep) questions, each narrow enough to search; those
    searches run in parallel with Google Search grounding; finally a synthesis
    step writes a brief with `[n]` citations against the sources that were
    actually retrieved. The panel shows the questions, the brief, every source
    with its URL, the token count, the credits charged and the balance after.
    Deep uses `gemini-2.5-pro`; standard uses `gemini-2.5-flash`. Both are
    environment overrides (`AI_CHAT_MODEL`, `AI_PLAN_MODEL`, `AI_SEARCH_MODEL`,
    `AI_RESEARCH_MODEL`).
  - **Insertion is an ordinary edit.** "Add to document" converts the Markdown
    into the same blocks the editor owns (headings keep the structure the
    presentation converter reads), appends a "Sources" section with real links,
    and marks the document dirty. Nothing is written behind the editor's back.
  - **1 credit = 1,000 tokens**, input and output, rounded up, minimum 1.
    The cost is computed from the `usageMetadata` the provider reports — never
    estimated. If the provider reports no usage, the request fails rather than
    guessing a price.
  - **Charging is incremental.** Each step of a research run is charged as it
    completes, through `indra_spend_ai()` with the service role. A run that
    exhausts the balance stops, keeps what was written, and says so
    (`exhausted: true`) — the balance never goes below zero.
  - **Three tiers, editable on the server.** `indra_plans` holds Free (100
    credits/day, ₹0), Basic (600, ₹299) and Pro (2,500, ₹899). The
    administrator edits the daily allowance, name and price from
    Admin → Credits; a change applies from each account's next daily reset.
  - **Daily reset on the server's clock.** `pg_cron` runs
    `indra_reset_all_daily()` at 00:05 UTC. `indra_ensure_credit_day()` is the
    safety net: a balance is topped to its allowance the first time it is read
    after midnight, so a missed schedule or a laptop that was closed overnight
    cannot strand anybody.
  - **Purchases are requests.** No card, no gateway. A plan change or a top-up
    is a row in `indra_purchase_requests`; the administrator approves or
    declines it in Admin → Credits, and approval sets the plan (30 days) or adds
    purchased credits (which never expire and are spent after the daily
    allowance). Duplicate pending requests are refused by a partial unique
    index.
  - **Two gates on the admin console.** The local administrator session, and
    the server's own check that the signed-in cloud account holds the
    administrator role. With the second missing, Admin → Credits renders
    read-only and says why.
  - **The app never holds authority.** `indra_spend_ai`,
    `indra_ensure_credit_day` and `indra_reset_all_daily` are revoked from
    `authenticated`/`anon` and granted only to `service_role`;
    `grant update` on `indra_users` is narrowed to username, display name and
    contact address, so no client can write a balance column. SQLite keeps the
    last balance for display with the time it was true, and it is never
    consulted before a request.
  - **Offline is honest.** AI needs a route out; a request is refused rather
    than queued, and the panel says so. The Credits screen draws the last known
    balance, labelled as such, and refreshes when the cloud is reachable.

7. SECURITY MODEL
-----------------
Everything the app renders is treated as hostile, because a document is a file
that can be shared.

  - Editor markup is allowlisted on write AND on read (src/main/lib/sanitize.ts).
    Scripts, event handlers, javascript: URLs, iframes and inline styles are
    discarded, including in documents written before the allowlist existed.
  - The renderer has no filesystem or database access: sandbox, contextIsolation,
    no nodeIntegration, typed IPC only, CSP in the packaged app.
  - Every IPC handler re-validates its input and resolves the caller itself.
    Actor identity never comes from the renderer.
  - Administrator identity is a separate table and session; an admin session
    never grants access to project data through ordinary services, and a user
    session has no path to admin queries. backend:* and admin:* refuse to run
    without an admin session.
  - Admin sign-in is rate-limited (5 failures, 15 minutes) and audited.
  - Sessions live in the local database with an expiry (30 days user, 12 hours
    admin).
  - The optional Supabase public key is sealed with the OS keystore before it is
    stored, and the renderer only ever sees its last four characters.
  - Single-instance lock: a second launch focuses the existing window instead of
    opening a second writer on the same database.
  - Links in documents open in the default browser; the app shell never
    navigates away from itself.
  - The app refuses to store a Supabase service_role key at all, and says why.


8. THE SELF-UPDATER (the unusual part)
--------------------------------------
Constraint: the installer is used once, on a new machine. After that, updates
must happen inside the app, and no installer or downloaded executable may ever
be run.

Mechanism:
  - Each release publishes, besides the installer, a payload: the compiled app
    packed as one .asar (about 1 MB) plus payload.json naming it, its size and
    its SHA-256.
  - The running app fetches payload.json from
    https://github.com/<owner>/<repo>/releases/latest/download/payload.json,
    compares versions, downloads the payload to
    %APPDATA%\indra-hub\update\, verifies size and SHA-256, and records it in
    pending.json.
  - Applying an update is a restart. Bootstrap (out/main/bootstrap.js, the
    "main" entry in package.json) reads the record on the next start and, if the
    payload verifies, requires its main/index.js instead of the installed copy.
    Nothing is spawned and nothing is installed.
  - Checks run at startup (3 s delay), on window focus (at most hourly), every
    4 hours while open, and 10 minutes after a failure.

Failure behaviour — the point of the design:
  no payload                        → installed code runs
  wrong size or hash                → discarded, installed code runs
  payload older than the app        → ignored (never a downgrade)
  payload loads but never ready twice → dropped automatically on the third start
  everything fine                   → payload keeps running and reports its own
                                      version (runningVersion() reads the record,
                                      because app.getVersion() still reports the
                                      installed build)

Settings → Updates shows the installed build and the running build side by side;
when they differ, an in-app update is running.

THE ASAR TRAP — read this before touching fs in the updater
Electron's asar layer claims EVERY filesystem path that contains the string
".asar", not only the archive the app is loaded from
(lib/node/asar-fs-wrapper.ts, v45). It wraps stat, statSync, lstat, lstatSync,
readFile, readFileSync, access, accessSync, exists, existsSync, realpath,
readdir (and their promises forms), and hooks the open/read/fstat/close bindings.
Consequences that cost several releases:
  1. A temporary download named "<payload>.asar.part" is read as an entry INSIDE
     the archive and fails with "Invalid package <path>".
  2. fs.rm / fs.rmSync are built on lstat, so deleting a payload path throws the
     same error — the delete that precedes the rename broke every download.
  3. Stat-ing or hashing the payload archive itself is intercepted unless
     process.noAsar is true.
Fixes in place: downloads are written as "incoming-<name>.download" (no ".asar"
substring) and renamed only after verification; deleting uses unlink rather than
rm; raw reads and stats of payload files run inside a synchronous
`asPlainFile()` helper that sets process.noAsar and restores it. Rename and
unlink are not intercepted.

Tests for this exist and must keep passing:
  npm run sim:update   bundles the real updater, serves a real .asar over HTTP,
                       runs the check under a faithful copy of the asar layer,
                       then asks bootstrap whether it would adopt the result
  npm run sim:admin    seeds a throwaway database and signs in as the
                       administrator
  npm run sim:maintenance  proves sign-in and registration still work during
                       maintenance while data calls are refused
  npm run sim:appearance   proves the background-video pipeline: install,
                       copy, the exact bytes handed to the renderer, refusal of
                       fake, empty, H.265 and oversized files, the playback
                       health check, replacement, clamping, removal
  npm run sim:workspace    proves the shared workspace against a faithful fake
                       of GoTrue, PostgREST, Storage and Realtime: fresh
                       install, live change, claim, publish, video transfer,
                       stale write, hostile payload, offline, disconnect


8.5 THE SHARED WORKSPACE (1.6.0)
--------------------------------
  Storage          one row: public.indra_workspace, id 'primary', in the
                   project this build points at
  Constants        src/shared/workspace.ts — WORKSPACE_URL, WORKSPACE_KEY
                   (publishable key only; RLS is what protects the row)
  Schema           supabase/workspace.sql — table, trigger, RLS, the claim
                   function, the public view, the storage bucket and policies,
                   the Realtime publication
  Client           src/main/services/workspace.ts — mirror, reconcile, publish,
                   Realtime socket with a polling fallback
  Panel            Admin → Cloud & sync (components/WorkspacePanel.tsx)

  What is shared: allow_registration, maintenance (+ message),
  require_activation_key, and the sign-in background (asset id, mime, bytes,
  storage path, blur, dim).

  Who is the source of truth:
    - Once the row has an owner, the row is the source of truth. Until it has
      one, it overrules nobody: an unclaimed row still holds the values the
      project shipped with, because only an owner can ever write it, so
      applying it would silently undo whatever this machine's administrator has
      just done. That is exactly what went wrong in 1.6.0 (the first video
      upload after it disappeared within a minute); the rule is now explicit.
    - Claiming is the handover. The machine that claims publishes what it is
      already running — maintenance, registration, the message, the video and
      its treatment — so the fleet inherits the administrator's actual
      configuration instead of the row's untouched defaults.

  How it stays right:
    - The row is the source of truth once it has an owner. Every local edit is published with an
      optimistic revision filter; if another machine got there first, the
      patch updates nothing, this machine adopts their row and says so.
    - Every row this machine receives is untrusted input: blur and dim are
      clamped, the message is truncated, and only the four playable video types
      are accepted. A background that cannot be fetched or played leaves the
      previous one on screen and reports why; it never blocks the switches.
    - The renderer never sees a token, a URL or a key. Sessions are sealed with
      the OS keystore; all writes go through an administrator session.
    - No connection means the local mirror answers. The app opens, signs in and
      runs maintenance exactly as the last row said.
    - Realtime is a WebSocket subscription when the platform provides one, an
      eight-second poll when it does not, and a sixty-second reconcile either
      way. Windows are told to re-read through `workspace:changed`.
    - A setup code, stored only as a SHA-256, decides which account may claim
      the row; it is cleared when used. `anon` has no UPDATE grant at all.

  Fresh installs: the endpoint is compiled in, so a machine that has never been
  configured mirrors the row before the first sign-in screen is painted (and
  re-reads it the moment it lands). "Disconnect" in the panel is remembered in
  `workspace_opt_out`, so the next launch does not undo it.

  Known boundary: this section shares *configuration*. User data travels by a
  different route and a different identity — see 5.1d and section 10.

Stage 1 — database (DONE): supabase/schema.sql creates the cloud tables.
Stage 3 — the desktop client (DONE in 1.8.0): src/main/services/cloud.ts

  - 23 Row Level Security policies across 7 tables, a trigger on auth.users, and
    security-definer helpers: indra_find_member (max 5 results, never returns

  Proven by rolled-back probes: an unknown auth id reads 0 rows in all 7 tables;

are two cloud accounts, joined by a transfer code, not by signing in with the

disallowed_useragent), and no OAuth client has been configured. Team sharing of
a cloud copy (members writing to the owner's cloud project) is not built: the
cloud copy is the owner's.

The order was deliberate: a client holding a public key is only safe if the
database enforces the rules, so the rules had to exist and be proven first.

12. KNOWN LIMITATIONS / UNFINISHED WORK
---------------------------------------
Honest list; none of these are hidden:
  - The offline workspace is a single local profile per PC. Two people using one
    machine offline share it until one of them signs in and adopts the work.
  - Cloud copies are per installation. A second PC reaches them only by
    adopting a transfer code from the first (Settings → Cloud); there is no
    person-level sign-in that would let two machines meet on their own.
  - Saving to the cloud mirrors the project: it replaces the cloud copy rather
    than merging two divergent versions, and every save rewrites it in full.
    At current project sizes that is a few requests; it is not a sync engine.
  - AI needs a provider key in the Edge Function's environment
    (`GEMINI_API_KEY`). Until one is set the function answers `not_configured`
    and the panel says AI is not switched on — it never fakes an answer.
  - Research runs are not streamed: the panel shows elapsed time while the run
    works, then the whole brief. A deep run is bounded by the Edge Function's
    wall clock (~135s of work by design) and can time out on a very broad topic.
  - Bring-your-own-key is not implemented. There is one workspace key and one
    balance per account; a person cannot yet point the app at their own key.
  - Plan changes and top-ups are approved by hand; there is no payment gateway
    and no invoice.
  - Google sign-in does not exist in the app and no OAuth client is configured.
  - The app is not wired to any hosted licensing service; activation keys are
    local rows in the local database.
  - The Windows installer is unsigned (SmartScreen warning).
  - Document autosave does not flush on window close, so the last edits of the
    final few seconds can be lost if the app is killed rather than closed.
  - Version history keeps 30 versions and rewrites the whole JSON content per
    save; fine at current document sizes, not tuned for very large ones.
  - Client-side ids are used as primary keys; there is no conflict resolution
    story for a future multi-device sync.
  - The rule-based converter fabricates no attributions, but quote slides keep
    whatever attribution the document gives; there is no citation model.
  - `overview.counts.documents` and a few dashboard numbers are computed with
    simple COUNT(*) queries and have shown 0 in some views; the source of truth
    is the counting code in src/main/services/admin.ts.
  - Admin → System reports file size only, not table-level growth.
  - No automated test suite beyond the simulations (sim:update, sim:admin, and
    the rest);
    everything else is verified by typecheck, build and manual runs.
  - Nothing in the app is localised; English only.


13. RULES THAT MUST NOT BE BROKEN
---------------------------------
These were decided deliberately and the user has rejected alternatives. Breaking
them is a regression, not a design choice.

  1. No installer during an update. The installed app replaces its own code with
     a verified payload and restarts. Never download or execute an .exe.
  2. The service_role / secret key never enters the desktop app. Only the
     publishable key.
  3. The renderer never touches the filesystem or the database; everything goes
     through typed IPC, and the main process resolves the caller itself.
  4. Administrator access is never advertised and never reachable from an
     ordinary user's screen; the main process refuses admin:* and backend:*
     without an admin session.
  5. Document HTML is allowlisted on write AND on read. Never render unsanitised
     markup.
  6. The updater must never be able to prevent the app from starting: a bad
     payload is discarded and the installed code runs.
  7. A payload that stops verifying is deleted, not retried forever.
  8. Releases are tag-driven; the workflow asserts the payload contains
     main/index.js and renderer/index.html before publishing.
  9. Platform conventions: no window.prompt, no native dialogs for app flows,
     no second instance of the app.
 10. Do not reintroduce the asar mistakes in section 8: no fs call in the update
     path may touch a path containing ".asar" except through the helpers, and
     "npm run sim:update" must pass.

15. WHERE THIS IS GOING NEXT
----------------------------
Stage 3 shipped in 1.8.0: a per-installation cloud identity, push, pull and a
transfer code, proven against the real database's policies.

The next honest step is person-level identity: system-browser Google sign-in
with PKCE and a loopback listener, so that signing in on a second PC finds the
same cloud copies without a transfer code. That needs an OAuth client in the
cloud console, and `indra_users` already links profiles to `auth.users`.

After that: team sharing of a cloud copy (a member writing to the owner's cloud
project under their own profile), and the licensing service that replaces local
activation keys.
