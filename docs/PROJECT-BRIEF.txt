This is a complete, self-contained description of the INDRA HUB project: what it
is, every feature that exists, how it is built, how it ships, what is proven,
and what is still missing. Read it as the full context for the codebase. It is
written so that nothing else is needed to start working on the project.

If you are an AI assistant receiving this: treat the "RULES THAT MUST NOT BE
BROKEN" section as hard constraints, and treat the "KNOWN LIMITATIONS" section as
the honest list of what is unfinished. Do not describe features that are not in
this document — they do not exist.


1. WHAT IT IS
-------------
INDRA HUB is a local-first desktop workspace for writing documents and turning
them into presentations. It runs entirely on the user's machine: accounts,
projects, documents, decks and settings all live in a single SQLite file. It
works with no network connection and needs no server.

Around that core sit three things:
  - teams: projects with an owner and members, with per-project access checks
  - an administration panel: a separate identity with its own session, able to
    manage accounts, projects, content, activation keys, app-wide switches and
    an audit log
  - a self-updater: the installed app updates itself from GitHub Releases by
    replacing a small code payload, without ever downloading or running an
    installer

The product constraint that shaped everything: the user installs a Windows
installer ONCE. Every later update must arrive inside the running app. The user
explicitly rejected "downloads the new installer and runs it".

4. ARCHITECTURE
---------------
Three processes, one rule: the renderer never touches the filesystem or the
database directly.

  src/main/index.ts        main process: window, menu, IPC registration, CSP,
                           single-instance lock, --reset-admin handling
  src/main/bootstrap.ts    the entry point of the packaged app (see section 8):
                           decides whether to run the installed code or a
                           downloaded payload
  src/main/ipc/index.ts    every IPC handler; each one validates its input and
                           resolves the caller itself (never trusts the renderer)
  src/main/services/*      business logic, one module per area:
                           auth, projects, users, documents, presentations,
                           graph, admin, activation, backend, settings, updates
  src/main/lib/*           payload (update storage + bootstrap), convert
                           (document → deck), sanitize, password, validation,
                           errors
  src/main/db/*            schema.ts (tables + migrations), database.ts
                           (connection, pre-migration backups)
  src/preload/index.ts     the typed bridge; the only surface the UI can call
  src/renderer/src/...     React UI
  src/shared/types.ts      the single source of truth for every shape crossing
                           IPC, and for constants like theme lists

Renderer isolation: sandbox on, contextIsolation on, nodeIntegration off, and a
Content Security Policy in the packaged app. The renderer talks to the main
process only through `window.indra`, defined in the preload; every call returns
`{ ok: true, data }` or `{ ok: false, error }` and the UI unwraps it in
`src/renderer/src/lib/api.ts`.

59 IPC channels exist, all namespaced: app:*, auth:*, projects:*, documents:*,
presentations:*, graph:*, updates:*, backend:*, admin:*.


5. FEATURE INVENTORY
--------------------

5.1 Accounts and sessions
  - Signed-out shell (1.6.3): the form sits in one centred column on an
    edgeless veil. No card, no border, no wordmark and no foot line — the only
    things on the screen are the heading, the fields, one button and one link.
    With the administrator's background video installed the film plays behind
    that column under a darkening and a blur, both faded out radially so the
    edges fall back to the desktop instead of framing a box. The column centres
    with margin-block so it still scrolls on a short window rather than being
    clipped.
  - Local registration with username, display name, email, password
  - Sign in with username OR email
  - scrypt hashing with per-record salt; constant-time verification
  - Sessions remembered for 30 days in the local database
  - Login throttling: 5 failed attempts locks sign-in for 15 minutes
  - Self-service: change display name / email, change password, delete account
    (password-confirmed)
  - Registration can be closed by the administrator
  - Registration can require an activation key
  - Maintenance mode: closes the WORKSPACE, never the front door. Signing in and
    registering always work; a signed-in account lands on the administrator's
    maintenance message, and every data call is refused in the main process
    while it is on. The administration panel stays reachable so it can be lifted
    from inside. Nothing on the maintenance screen points at administration.
  - The maintenance screen is a composed card, not a text column: status
    eyebrow with a live pulse, an automatic-checking pill, the administrator's
    message as a quoted panel, a three-part fact strip (account, workspace,
    last check), a quiet note, "Check now" / "Sign out", and an indeterminate
    activity line along the bottom edge. Same hairline grid as the sign-in
    canvas, light and dark, and it collapses to one column at narrow widths.

5.1b Offline (1.7.0)
  - The main process answers `net.isOnline()` every four seconds, re-reads it
    when the window is focused, and tells every window when it changes. No
    ping, no DNS lookup, no traffic: the operating system's own view.
  - The renderer mirrors it through ConnectivityProvider, with the browser's
    online/offline events as a second pair of eyes.
  - Offline, the app is the writing tool: the rail keeps Documents,
    Presentations, Projects and Settings; everything else redirects to
    Documents instead of rendering half-alive. The caption carries a quiet
    OFFLINE pill and the rail's only heading is OFFLINE.
  - Documents and Presentations are cross-project libraries (every document
    and deck the account can reach, most recent first, project named on each
    row). They exist online too — they are the quickest way back into work —
    but offline they are the whole workspace.
  - Nothing in the offline path touches the network: sign-in, registration,
    projects, documents, presentations, settings and the maintenance screen
    are all SQLite reads and writes.

5.1c Where work is kept (1.7.0)
  - The working copy is SQLite on the machine. It has never needed a
    connection and it is what every screen reads.
  - "Save a copy" on a project writes one .indrahub file through the system
    save dialog: project name and description, every document's blocks, every
    presentation's slides and its theme. Self-contained — no ids to resolve.
  - "Open a saved project" on the Projects screen reads one back as a NEW
    project owned by whoever opened it, so the same file can be opened twice,
    or on another machine, without touching the original.
  - Imported files are parsed, shape-checked, and pushed through the same
    block sanitiser as a typed document; a file that breaks halfway leaves no
    half-made project behind.
  - A cloud copy of project content is deliberately NOT shipped yet. The
    tables and RLS exist (supabase/schema.sql, auth.sql), but they key on
    `auth.uid()` and the app's accounts are local, so writing content to them
    today would either fail or pool every customer's work under one identity.
    That gate is cloud sign-in (section 15), and until it exists the app says
    "This PC" honestly rather than offering a button that pretends.

5.2 Home, teams and projects
  - Home is the first screen after signing in and the first item in the
    sidebar. Two panels and no more: the account (monogram, name, handle,
    email, member since, a link to settings) and the team.
  - One team per owner, created in place, renamed in place, deleted behind a
    confirmation. The roster lists the owner first, then members; a member is
    removed from the row itself. "Add member" searches registered accounts and
    offers only people who could actually join — never the owner, never
    somebody already on the roster, never a suspended account.
  - Being a member of somebody else's team is read-only and shows under
    "Member of"; ownership is checked in the service on every write, not in
    the renderer.
  - Teams are not projects: nothing in a project's data or permissions depends
    on them, and deleting a team touches no account and no document.
  - Create, rename, delete projects; each has a description
  - Owner/member model stored in project_members
  - Add members by searching existing users (username, display name, email —
    email only shown to project members)
  - Membership checks on every read and write in the service layer
  - Project dashboard: overview, members, documents, presentations, activity
  - Project workspace: a combined view of the project's material

5.3 Document Studio

    paragraph (inline rich text), bulleted list, numbered list, quote, code,
    divider, table (first row is the header), image (embedded source with alt

  - Autosave with a debounce; explicit save also available
  - Word and character counts
  - Version history: the last 30 versions per document, with restore
  - Every write passes through the sanitiser allowlist (see section 7)

5.4 Presentation Studio

  - Nine slide layouts: title, section, text, bullets, process, quote, table,

  - Reorder slides, edit, delete

  - "Stale source" detection: if the source document changed after conversion,

  - Conversion is deterministic and offline (src/main/lib/convert.ts): fixed

5.5 Project Intelligence

5.10 Design, theme and motion
  - Two themes, one set of tokens. Components never hold a colour of their own;
    everything reads --bg, --surface, --chrome, --line, --ink and the single
    wine accent from :root / .dark.
  - Matte black: canvas #0a0a0b, chrome (title bar and rail) #0d0d0f, panels
    #121214, wells (inputs) #0c0c0e, hairlines #1f2023. Depth comes from a
    1px light along the top edge of a raised panel, never from a glow. A
    selected surface is a 6% lift of the ink, so the accent stays on markers
    and icons instead of tinting whole blocks.
  - Light: canvas #f4f4f5, chrome #fbfbfc, panels #ffffff, hairlines #e4e4e8.
  - Radii 10 / 7 / 14, one easing curve (0.16, 1, 0.3, 1) and five durations.
  - Motion: route entrances (page, then rows 26ms apart), a panel cascade on
    two-column pages, project rows lifting 1px under the pointer, buttons
    compressing on press, nav icons nudging, monograms scaling, a modal rise,
    a cross-fade when the theme changes, and the title-bar view name fading
    over. Everything animates transform and opacity only — no layout, no
    filter, nothing that re-rasterises a surface — and prefers-reduced-motion
    zeroes the lot. The scrolling pane resets to the top on navigation.

6. DATA MODEL (SQLite)
----------------------
Fifteen tables, created by ordered migrations in src/main/db/schema.ts; the
schema version is stored in PRAGMA user_version and MIGRATION_COUNT tracks the
number of migrations (seven, the last of which added teams).

  users              id, username, display_name, email, password_hash,
                     password_salt, created_at, suspended_at
  projects           id, name, description, owner_id, created_at, updated_at
  project_members    project_id, user_id, added_at
  teams              id, name, owner_id, created_at, updated_at — one per
                     owner, enforced by a unique index on owner_id
  team_members       team_id, user_id, role, joined_at; the owner is not a
                     row here, a trigger refuses any attempt to insert one
  documents          id, project_id, title, content (JSON blocks), version,
                     created_by, created_at, updated_at
  document_versions  id, document_id, version, content, created_at
  presentations      id, project_id, title, theme, conversion_mode,
                     source_document_id, created_by, timestamps
  presentation_slides id, presentation_id, position, layout, title, body,
                     bullets, table, image, notes
  activation_keys    id, code_hash, masked_code, label, created_at, expires_at,
                     used_at, used_by
  admin_users        id, email, display_name, password_hash, password_salt,
                     created_at, last_sign_in_at
  admin_audit        id, admin_id, action, detail, created_at
  app_settings       singleton row of app-wide switches (registration,
                     maintenance, activation keys, login background asset id,
                     background blur and dim)
  media_assets       id, kind, file_name, original_name, mime, bytes,
                     created_at — the database record for administrator-
                     installed media; the bytes themselves live in
                     <userData>/media, are read by the main process and handed
                     to the renderer over IPC, which plays them from a Blob URL
  app_state          key/value store: session, admin session, throttle records,
                     update state

Before any migration that changes an existing database, the file is copied to
`backups/` beside it (five most recent kept). A fresh install copies nothing.


7. SECURITY MODEL
-----------------
Everything the app renders is treated as hostile, because a document is a file
that can be shared.

  - Editor markup is allowlisted on write AND on read (src/main/lib/sanitize.ts).
    Scripts, event handlers, javascript: URLs, iframes and inline styles are
    discarded, including in documents written before the allowlist existed.
  - The renderer has no filesystem or database access: sandbox, contextIsolation,
    no nodeIntegration, typed IPC only, CSP in the packaged app.
  - Every IPC handler re-validates its input and resolves the caller itself.
    Actor identity never comes from the renderer.
  - Administrator identity is a separate table and session; an admin session
    never grants access to project data through ordinary services, and a user
    session has no path to admin queries. backend:* and admin:* refuse to run
    without an admin session.
  - Admin sign-in is rate-limited (5 failures, 15 minutes) and audited.
  - Sessions live in the local database with an expiry (30 days user, 12 hours
    admin).
  - The optional Supabase public key is sealed with the OS keystore before it is
    stored, and the renderer only ever sees its last four characters.
  - Single-instance lock: a second launch focuses the existing window instead of
    opening a second writer on the same database.
  - Links in documents open in the default browser; the app shell never
    navigates away from itself.
  - The app refuses to store a Supabase service_role key at all, and says why.


8. THE SELF-UPDATER (the unusual part)
--------------------------------------
Constraint: the installer is used once, on a new machine. After that, updates
must happen inside the app, and no installer or downloaded executable may ever
be run.

Mechanism:
  - Each release publishes, besides the installer, a payload: the compiled app
    packed as one .asar (about 1 MB) plus payload.json naming it, its size and
    its SHA-256.
  - The running app fetches payload.json from
    https://github.com/<owner>/<repo>/releases/latest/download/payload.json,
    compares versions, downloads the payload to
    %APPDATA%\indra-hub\update\, verifies size and SHA-256, and records it in
    pending.json.
  - Applying an update is a restart. Bootstrap (out/main/bootstrap.js, the
    "main" entry in package.json) reads the record on the next start and, if the
    payload verifies, requires its main/index.js instead of the installed copy.
    Nothing is spawned and nothing is installed.
  - Checks run at startup (3 s delay), on window focus (at most hourly), every
    4 hours while open, and 10 minutes after a failure.

Failure behaviour — the point of the design:
  no payload                        → installed code runs
  wrong size or hash                → discarded, installed code runs
  payload older than the app        → ignored (never a downgrade)
  payload loads but never ready twice → dropped automatically on the third start
  everything fine                   → payload keeps running and reports its own
                                      version (runningVersion() reads the record,
                                      because app.getVersion() still reports the
                                      installed build)

Settings → Updates shows the installed build and the running build side by side;
when they differ, an in-app update is running.

THE ASAR TRAP — read this before touching fs in the updater
Electron's asar layer claims EVERY filesystem path that contains the string
".asar", not only the archive the app is loaded from
(lib/node/asar-fs-wrapper.ts, v45). It wraps stat, statSync, lstat, lstatSync,
readFile, readFileSync, access, accessSync, exists, existsSync, realpath,
readdir (and their promises forms), and hooks the open/read/fstat/close bindings.
Consequences that cost several releases:
  1. A temporary download named "<payload>.asar.part" is read as an entry INSIDE
     the archive and fails with "Invalid package <path>".
  2. fs.rm / fs.rmSync are built on lstat, so deleting a payload path throws the
     same error — the delete that precedes the rename broke every download.
  3. Stat-ing or hashing the payload archive itself is intercepted unless
     process.noAsar is true.
Fixes in place: downloads are written as "incoming-<name>.download" (no ".asar"
substring) and renamed only after verification; deleting uses unlink rather than
rm; raw reads and stats of payload files run inside a synchronous
`asPlainFile()` helper that sets process.noAsar and restores it. Rename and
unlink are not intercepted.

Tests for this exist and must keep passing:
  npm run sim:update   bundles the real updater, serves a real .asar over HTTP,
                       runs the check under a faithful copy of the asar layer,
                       then asks bootstrap whether it would adopt the result
  npm run sim:admin    seeds a throwaway database and signs in as the
                       administrator
  npm run sim:maintenance  proves sign-in and registration still work during
                       maintenance while data calls are refused
  npm run sim:appearance   proves the background-video pipeline: install,
                       copy, the exact bytes handed to the renderer, refusal of
                       fake, empty, H.265 and oversized files, the playback
                       health check, replacement, clamping, removal
  npm run sim:workspace    proves the shared workspace against a faithful fake
                       of GoTrue, PostgREST, Storage and Realtime: fresh
                       install, live change, claim, publish, video transfer,
                       stale write, hostile payload, offline, disconnect


8.5 THE SHARED WORKSPACE (1.6.0)
--------------------------------
  Storage          one row: public.indra_workspace, id 'primary', in the
                   project this build points at
  Constants        src/shared/workspace.ts — WORKSPACE_URL, WORKSPACE_KEY
                   (publishable key only; RLS is what protects the row)
  Schema           supabase/workspace.sql — table, trigger, RLS, the claim
                   function, the public view, the storage bucket and policies,
                   the Realtime publication
  Client           src/main/services/workspace.ts — mirror, reconcile, publish,
                   Realtime socket with a polling fallback
  Panel            Admin → Cloud & sync (components/WorkspacePanel.tsx)

  What is shared: allow_registration, maintenance (+ message),
  require_activation_key, and the sign-in background (asset id, mime, bytes,
  storage path, blur, dim).

  Who is the source of truth:
    - Once the row has an owner, the row is the source of truth. Until it has
      one, it overrules nobody: an unclaimed row still holds the values the
      project shipped with, because only an owner can ever write it, so
      applying it would silently undo whatever this machine's administrator has
      just done. That is exactly what went wrong in 1.6.0 (the first video
      upload after it disappeared within a minute); the rule is now explicit.
    - Claiming is the handover. The machine that claims publishes what it is
      already running — maintenance, registration, the message, the video and
      its treatment — so the fleet inherits the administrator's actual
      configuration instead of the row's untouched defaults.

  How it stays right:
    - The row is the source of truth once it has an owner. Every local edit is published with an
      optimistic revision filter; if another machine got there first, the
      patch updates nothing, this machine adopts their row and says so.
    - Every row this machine receives is untrusted input: blur and dim are
      clamped, the message is truncated, and only the four playable video types
      are accepted. A background that cannot be fetched or played leaves the
      previous one on screen and reports why; it never blocks the switches.
    - The renderer never sees a token, a URL or a key. Sessions are sealed with
      the OS keystore; all writes go through an administrator session.
    - No connection means the local mirror answers. The app opens, signs in and
      runs maintenance exactly as the last row said.
    - Realtime is a WebSocket subscription when the platform provides one, an
      eight-second poll when it does not, and a sixty-second reconcile either
      way. Windows are told to re-read through `workspace:changed`.
    - A setup code, stored only as a SHA-256, decides which account may claim
      the row; it is cleared when used. `anon` has no UPDATE grant at all.

  Fresh installs: the endpoint is compiled in, so a machine that has never been
  configured mirrors the row before the first sign-in screen is painted (and
  re-reads it the moment it lands). "Disconnect" in the panel is remembered in
  `workspace_opt_out`, so the next launch does not undo it.

  Known boundary: this shares *configuration*, not user data. Projects,
  documents and presentations are still local to each machine; shipping them
  to the cloud is the next step, and it needs the per-user identity work in
  docs/SUPABASE.md.


9. BUILD AND RELEASE
--------------------
Development:        npm install, npm run dev, npm run typecheck, npm run build
Production build:   electron-vite build, then a separate Vite build that emits
                    out/main/bootstrap.js
Release:            pushing a tag v* triggers .github/workflows/release.yml on
                    windows-latest:
                      - npm ci, typecheck, build
                      - pack out/ into payload/, then into
                        release/INDRA-HUB-Payload-<version>.asar
                      - assert the archive contains main/index.js and
                        renderer/index.html (a payload without them would fail
                        silently at the next start)
                      - assert app-update.yml exists in the packaged app
                      - electron-builder --win → NSIS installer + blockmap
                      - write payload.json {version, file, sha256, size, url}
                      - publish a GitHub Release with: the .exe, latest.yml,
                        the .blockmap, the payload .asar, payload.json
                    Assets per release:
                      INDRA-HUB-Setup-<version>.exe        ~123 MB
                      INDRA-HUB-Setup-<version>.exe.blockmap ~130 KB
                      INDRA-HUB-Payload-<version>.asar       ~1.0 MB
                      latest.yml, payload.json
                    A run takes about 4–5 minutes.

The installer is unsigned, so Windows SmartScreen shows "Windows protected your
PC" on first install; "More info → Run anyway" gets past it. Code signing needs
a certificate the project does not have.

Updating requires the repository to be public: GitHub refuses anonymous requests
for a private repository's releases, and the alternative — a token compiled into
the app — is not acceptable.


10. SUPABASE (optional cloud, partially done)
---------------------------------------------
The app is local-first. Supabase is an optional cloud copy, configured by an
administrator in Admin → Backend with the project URL and the PUBLIC key. The
panel proves the connection and reports whether the schema is in place.

Project: ref cztyznuoferktewdhyji, region ap-northeast-2, PostgreSQL 17.
Public key: sb_publishable_RVaLkA8l6LOJ4ARqa38tzA_tFuCQqDA
The service_role / secret key is NEVER allowed in the app: it bypasses Row Level
Security, and anyone who unpacked the installer would own the whole database.

Stage 1 — database (DONE): supabase/schema.sql creates the cloud tables.
Stage 2 — identity (DATABASE DONE, CLIENT PENDING): supabase/auth.sql adds
  - member numbers: IH-<YYYY>-<6 digits>, minted once from a sequence at profile
    creation, never writable by a client
  - Supabase Auth with Google as the intended provider
  - 23 Row Level Security policies across 7 tables, a trigger on auth.users, and
    security-definer helpers: indra_find_member (max 5 results, never returns
    email), indra_project_roster, indra_ensure_profile, indra_claim_admin
  - column-level grants so a user may update only their own username and
    display_name; self-promotion to admin is refused by the database
  Proven by rolled-back probes: an unknown auth id reads 0 rows in all 7 tables;
  anon reads 0; an owner sees exactly their own project and document; a second
  user sees nothing and `in_project` is false; a self-add to a project is refused
  by policy; a self-promotion is refused by grant; a new auth row mints
  IH-2026-000001.

What is NOT done: the desktop client is not wired to Supabase Auth. Accounts,
sessions and documents are still local. Nothing is synced and nothing leaves the
machine. Sign-in by Google must happen in the SYSTEM BROWSER with PKCE and a
loopback redirect — Google refuses OAuth inside embedded webviews
(disallowed_useragent), and Firebase's signInWithPopup is a web API that does not
exist in Electron.

The order was deliberate: a client holding a public key is only safe if the
database enforces the rules, so the rules had to exist and be proven first.


11. THE ADMINISTRATOR
---------------------
Every installation ships with exactly one administrator, created at startup
before any window exists:

  Email:     admintej@gmail.com
  Password:  AAaa1234@$

  - Stored as a scrypt hash; the database never holds the plain text.
  - Created once. A second start, or an installation that already has an
    administrator, changes nothing.
  - Reached only at Ctrl+Alt+A (Cmd+Alt+A on macOS) or #/admin. Nothing on the
    Sign in or Register screens mentions it — that invitation was removed in
    1.4.0.
  - Any other email is refused; five failures lock the gate for 15 minutes.
  - The password travels inside the application files, so it is a starting
    credential, not a secret. Admin → Access & controls replaces the email, the
    display name and the password; do that before distributing the app.
  - `INDRA HUB.exe --reset-admin` removes the identity and deliberately does not
    recreate the shipped account, so a reset means the operator chooses. It is
    command-line only on purpose: recovering access should require control of
    the machine, the same bar as opening the database file.


12. KNOWN LIMITATIONS / UNFINISHED WORK
---------------------------------------
Honest list; none of these are hidden:
  - The desktop client is not connected to Supabase Auth. No accounts, projects
    or documents are synced to the cloud. Google sign-in does not exist yet in
    the app, and no OAuth client has been configured.
  - The app is not wired to any hosted licensing service; activation keys are
    local rows in the local database.
  - The Windows installer is unsigned (SmartScreen warning).
  - Document autosave does not flush on window close, so the last edits of the
    final few seconds can be lost if the app is killed rather than closed.
  - Version history keeps 30 versions and rewrites the whole JSON content per
    save; fine at current document sizes, not tuned for very large ones.
  - Client-side ids are used as primary keys; there is no conflict resolution
    story for a future multi-device sync.
  - The rule-based converter fabricates no attributions, but quote slides keep
    whatever attribution the document gives; there is no citation model.
  - `overview.counts.documents` and a few dashboard numbers are computed with
    simple COUNT(*) queries and have shown 0 in some views; the source of truth
    is the counting code in src/main/services/admin.ts.
  - Admin → System reports file size only, not table-level growth.
  - No automated test suite beyond the two simulations (sim:update, sim:admin);
    everything else is verified by typecheck, build and manual runs.
  - Nothing in the app is localised; English only.


13. RULES THAT MUST NOT BE BROKEN
---------------------------------
These were decided deliberately and the user has rejected alternatives. Breaking
them is a regression, not a design choice.

  1. No installer during an update. The installed app replaces its own code with
     a verified payload and restarts. Never download or execute an .exe.
  2. The service_role / secret key never enters the desktop app. Only the
     publishable key.
  3. The renderer never touches the filesystem or the database; everything goes
     through typed IPC, and the main process resolves the caller itself.
  4. Administrator access is never advertised and never reachable from an
     ordinary user's screen; the main process refuses admin:* and backend:*
     without an admin session.
  5. Document HTML is allowlisted on write AND on read. Never render unsanitised
     markup.
  6. The updater must never be able to prevent the app from starting: a bad
     payload is discarded and the installed code runs.
  7. A payload that stops verifying is deleted, not retried forever.
  8. Releases are tag-driven; the workflow asserts the payload contains
     main/index.js and renderer/index.html before publishing.
  9. Platform conventions: no window.prompt, no native dialogs for app flows,
     no second instance of the app.
 10. Do not reintroduce the asar mistakes in section 8: no fs call in the update
     path may touch a path containing ".asar" except through the helpers, and
     "npm run sim:update" must pass.

15. WHERE THIS IS GOING NEXT
----------------------------
The natural next step is wiring the desktop client to Supabase Auth (Stage 3):
system-browser Google sign-in with PKCE and a loopback listener, refresh token

and the licensing service that replaces local activation keys.
